# M1 战斗灰盒 · 开发追踪指南

> 本文档是 M1「核心战斗闭环」的施工图，用于直接驱动 vibe coding 写代码。每张任务卡对应一个可验证的功能点，AI（或开发者）每次只处理一张卡：实现 → 按卡内验证方式验证 → 勾选完成 → 进入下一张。
>
> 配套文档：`03_核心玩法设计.md`（玩法规则）、`05_Battle_模块设计.md`（模块边界）、`06_里程碑规划与任务依赖.md`（M1 验收标准）、`05_性能优化与埋点日志.md`（对象池/埋点纪律）。

## 使用说明（vibe coding 流程）

> 会话续接：先读 `09_开发日志_会话交接.md`（进度快照/关键坑/下一步），再按本指南逐卡执行。

1. 按 Phase 顺序处理任务卡，**不跳 Phase**（依赖关系见各卡"前置"字段）
2. 每张卡只改"涉及文件"列出的文件，禁止顺手改其他模块
3. 每张卡完成后必须跑"验证方式"；验证不过 → 回到实现，不许带着未验证状态进入下一卡
4. 卡内"不做"清单是硬边界，AI 不得自行扩展
5. 完成一张卡即 `git commit`，提交信息带卡号（如 `feat(battle): T1.2 弹匣与换弹机制`）
6. 所有状态为"完成"的卡勾选 `[x]`

## 全局工程纪律（每张卡都要遵守）

1. **数据优先**：伤害/冷却/血量/掉率一律进配置（`BattlePlayerConfig`、新增 SO、或 `[Serializable]` 数据类），禁止硬编码魔法数字
2. **对象池**：战斗内高频对象（子弹/飘字/敌人子弹）一律走 `BattleObjectPool`，禁止新增 `Instantiate`/`Destroy` 高频路径
3. **无每帧 GC**：Update/FixedUpdate 路径禁止 LINQ、闭包捕获、字符串拼接、每帧 `GetComponent`
4. **事件驱动**：系统间通信走 QFramework 事件（`SendEvent`/`RegisterEvent`），禁止模块间直接引用
5. **owner 纪律**：改任何文件前确认该功能真正属于该文件；`Before/` 目录禁止修改
6. **不扩展**：卡内"不做"清单是硬边界；发现新需求 → 开新卡，不塞进当前卡
7. **提交纪律**：每卡完成即 commit，信息带卡号
