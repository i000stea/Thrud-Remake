## 0. 结论摘要

1. **维持 D02**。对比全部候选后，代码层 HybridCLR 在 Unity 2022.3 + 纯 C# 工程上领先幅度明显（无需胶水层、支持热更 MonoBehaviour/ScriptableObject、支持多线程与 async），资源层 YooAsset 是本工程既有 ResKit 路线最平顺的升级目标。
2. **版本建议**：HybridCLR `com.code-philosophy.hybridclr` **v8.14.1**（2026-08-19 tag）；YooAsset **3.0.5**（2026-07-20 release）。均为各自当前最新稳定版。
3. **社区版足够**，不需购买商业版：商业版独有的是 DHE 差分混合执行、完全泛型共享、元数据优化、热重载、代码加固。本工程的代价是**必须走"补充元数据"路线**（见 §4.1）。
4. **三项工程配置必须先改**（已实测确认当前值）：
   - Android 的 `Api Compatibility Level` 从 `.NET Standard 2.1` 改为 `.NET Framework`（HybridCLR 硬要求）
   - PC 验证需要 `Standalone` 切 IL2CPP（当前是 Mono）→ 需安装 Windows Build Support (IL2CPP) 模块
   - YooAsset 3.x 依赖 SBP（`com.unity.scriptablebuildpipeline` ≥ 1.21.x），当前 `manifest.json` **没有**该包
5. **两项大工作**：① 资源层从 QFramework ResKit 迁到 YooAsset（含 UIKit 面板加载适配，这是本次最大工作量）；② 程序集/目录完整拆分（`Tea.Framework` AOT / `Tea.Game`+`Tea.Data` 热更）。当前工程只有**一个** `TeaGame.asmdef`。
6. **主线不打断**：本计划对应 M0（热更链路全通），与 M1 战斗灰盒/Demo 外放线并行推进时，**P1C 的程序集拆分**会大范围移动文件（该目录重构已于 2026-09-15 由用户手动提交 `5bc3890c`，工作区现已干净）。
7. **阶段编号已重排（2026-09-15 用户确认）**：原 P0–P5 与临时插入的两个记号（曾称 `P0A`/`P0B`）统一改为 **P1A 通读代码 + 清理冗余代码 → P1B 更新 Unity 版本 → P1C 热更新适配（HybridCLR + YooAsset）→ P2 → P3**，其余迭代内容顺延。记号映射表见 §5。当前执行 **P1A**（详见 §5A），下一阶段 **P1B**（详见 §5B）。

8. **引擎版本路线已定（2026-09-15 用户确认）**：**现在不切引擎**；P1A 先行，**P1B 引擎升级（目标 Unity 6.3 LTS）排在 P1A 之后、M2 内容扩张之前**，且必须在 P1C 之前完成。依据与前置清单见 **§5B**。核心事实：2022.3 LTS 安全支持已于 2025-05-07 结束。

> **执行顺序（2026-09-15 起）**：**P1A 通读 + 清理（当前）** → **P1B 引擎升级至 Unity 6.3 LTS** → **P1C 热更新适配（拆程序集 + HybridCLR + YooAsset）** → P2 更新流程与本地模拟服务器 → P3 Android 真机与打包一键化 → M2/M3 内容。

## 4. 方案细节要点（直接影响实现，摘自官方文档）

### 4.1 HybridCLR 的能力边界与代价

**不支持的特性（官方清单，全部 5 条）**：

1. `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.xxx)]` —— 纯时机问题：Unity 收集这些函数的时机远早于热更 dll 加载。**规避**：用反射收集，在合适时机主动调用。
2. 不支持对解释代码做 C# 级断点调试（官方未实现调试器）。
3. 不支持 `Marshal.StructureToPtr` 之类序列化结构的函数（普通 Marshal 函数可用）。
4. `[RequireComponent(typeof(AAA))]` 要求 `AAA` 已在别处实例化或 `AddComponent` 过，否则 Unity 会当作非脚本忽略。
5. v8.0.0 起支持热更脚本中定义 extern 函数，但返回值与参数有限制。

**AOT 泛型 —— 唯一的真实工程负担**：

- 热更代码中**自定义的**泛型类无限制；受限制的是 **AOT 程序集泛型**。il2cpp 是 AOT 运行时，只实例化过 `List<int>` / `List<string>` 时，热更代码里能用 `new List<int>()`，但**不能**用 `new List<float>()`。
- 社区版解决手段是**补充元数据**（`HybridCLR.RuntimeApi.LoadMetadataForAOTAssembly`）：为 AOT assembly 补上丢失的泛型函数体 IL 元数据。加载时机建议在热更完成后、执行任何热更代码前；**没有加载顺序要求**，只需使用前调用一次。
- 代价：补充元数据加载后约占 **dll 大小的 3–6 倍内存且不可回收**；被补充的泛型函数以解释方式执行（性能低于 AOT）。官方提供 `AOTAssemblyMetadataStripper` 剔除无关元数据（实测 mscorlib 可减 37.9%、System 减 66.2%）。
- 需要补充的 assembly 列表由 `HybridCLR/Generate/AOTGenericReference` 生成到 `AOTGenericReferences.cs`（`PatchedAOTAssemblyList`）。列表偏保守，无内存压力时全补最省事。
- 元数据模式：`SuperSet`（可用原始 AOT dll，工作流省事、内存占用更高）vs `Consistent`（必须用打包时裁剪后的 dll，一致但更易因微小差异加载失败）。**推荐 SuperSet**（官方也推荐新手用它）。
- 注意：`HomologousImageMode::Consistent` 模式下必须使用打包时生成的裁剪 dll（`HybridCLRData/AssembliesPostIl2CppStrip/{target}`），**不同 BuildTarget 的裁剪 dll 不可复用**，且**不要每次热更都用最新生成的 AOT dll**。
- 纪律落到本项目：02 文档要求的"新增框架层泛型 API 时登记进补充元数据列表"要继续执行；热更代码中避免 `List<热更定义的值类型>`（补充元数据可覆盖，但需确保对应 AOT dll 在补充列表内）。

**构建管线的自动行为（省去手工操作）**：

- 打包时自动把热更 assembly 从 build assemblies 中排除（`FilterHotFixAssemblies`）。
- 打包时自动把热更 dll 名写入 assembly 列表（`PatchScriptingAssemblyList`）—— 这是**资源上挂热更 MonoBehaviour 能被正确识别**的前提。
- 打包时自动备份裁剪后的 AOT dll 到 `HybridCLRData/AssembliesPostIl2CppStrip/{platform}`。
- 自动设置 `Scripting Backend = il2cpp`、`Api Compatibility Level = .NET Framework`，并在版本 < v4.0.0 时关掉增量式 GC（本工程 v8.14.1，无需管这条）。
- 更新 HybridCLR 后必须清 `Library/Il2cppBuildCache`（Installer 会自动清）。

**环境前置（Windows）**：git、Visual Studio 2019+ 且包含"使用 Unity 的游戏开发"+"使用 C++ 的游戏开发"组件、目标平台 IL2CPP 模块。安装方式为 `HybridCLR/Installer...`，它从 gitee 克隆 `hybridclr` + `il2cpp_plus` 并合并出含 HybridCLR 的 libil2cpp，落到 `{project}/HybridCLRData/LocalIl2CppData-{platform}/`（本地安装，通过进程内 `UNITY_IL2CPP_PATH` 生效，不影响其它项目）。网络不通时可"从本地复制 libil2cpp"安装。

**`link.xml` 冲突**：`HybridCLR/Settings` 的 `outputLinkFile` **千万不要**指向 `Assets/link.xml`（每次生成会覆盖）。本工程已有 `Assets/link.xml`（保留 MeshCollider 等引擎类型，见 14 文档 T0-4），两者必须分开。

### 4.2 YooAsset 3.x 的关键变化（相对 2.3）

- **推荐新工程直接用 3.x**（官方原话）：适合多包裹、多平台、自定义文件系统场景，为后续扩展留了更清晰的底子。
- 架构拆分：`YooAssets`（全局生命周期/包裹注册） / `ResourcePackage`（单包裹入口） / `ResourceManager`（加载与内存生命周期）。
- 初始化、请求版本、加载清单、下载、解压、导入、实例化、卸载**统一改为 Options 模型**。
- 文件系统重构：`BuiltinFileSystem` / `SandboxFileSystem` / `WebServerFileSystem` / `WebNetworkFileSystem`；`FileSystemHost` 统一管理文件系统、清单与 bundle 路由。
- 新增 `ArchiveFileBuildPipeline`：同 bundle 名下多个原生文件合并为归档文件，适合**配置表等大量小文件**场景（正对本工程的 `config` 分组）。
- 编辑器缓存目录从项目根 `yoo/` 迁到 **`Library/yoo/`**（升级后需手删旧目录）。
- 兼容层：定义编译宏 `YOOASSET_LEGACY_API` 可让大部分 2.3 代码零修改编译通过（兼容 API 标 `[Obsolete]`）。无法兼容的手动项包括：默认包裹快捷 API（`YooAssets.LoadAssetAsync(...)` 等约 50 个静态方法）已彻底移除，必须改为 `package.Xxx(...)`；`LoadSceneAsync` 的 `suspendLoad` 参数语义反转为 `allowSceneActivation`；解密服务接口拆分为 `IBundleOffsetDecryptor` 等。**本工程是全新接入，不启用兼容层，直接用 3.x API。**
- 常见坑（官方 FAQ，与本工程相关度高的）：
  - 构建产物目录默认在 `Bundles/{平台}/{包裹名}/`，与现有 `StreamingAssets/AssetBundles/` 不冲突，迁移期可共存。
  - 编辑器**模拟模式**下改资源后若卡顿，是每次调用 `EditorSimulateBuildInvoker.Build()` 重新生成清单导致，应改为手动生成一次并直接指定目录。
  - 增量打包后"下载数量为 0"通常是 `Copy Builtin File Option` 一直是 `Clear And Copy All` 导致内置目录已含最新资源。
  - 多包裹时勾 `Unique Bundle Name`，否则真机报 `The AssetBundle '__data' can't be loaded because another AssetBundle with the same files is already loaded`。
  - 加载定位地址**大小写敏感**；`Failed to mapping location to asset path` 基本是 location 写错。

### 4.3 与现有 ResKit / UIKit 的衔接

- **UIKit 面板加载**：现由 `SupportOldQF` 的 `ResKitPanelLoaderPool` 走 ResKit AB 常量（`QAssetBundle`）。迁移做法是在 `Tea.Framework` 里写一个 YooAsset 版 `IPanelLoaderPool` 适配层，`UIKit` 本身不动（02 文档既定策略）。`QAssetBundle` 生成常量退化为 YooAsset 的 location 字符串来源。

### 5A.1 为什么这个阶段是必要的（实测取证，2026-09-15）

以下全部是本次对仓库的实测结果，不是推测：

| 症状 | 实测证据 | 为什么这会让你"掌控不了方向" |

| **A 类：只活在禁用资产里** | `4BattleScene`、`5BattleScene-Test0/1`、**`Enemy_0Base.prefab`（2026-09-15 已由用户删除）**、`Battle EnemyUIData.asset` | `EnemyControl`、`EnvEffectControl`、`StoreBattleRoleData`、`EnemyUIData`（`EnemyEntity_Main` 的唯一挂载点已随基座 prefab 一起消失） | 摘组件后删脚本；`EnemyUIData` 是**数据资产**（随脚本一起删），需先解除三个场景对它的引用 |

**操作铁律：先摘组件，后删脚本。** 顺序颠倒就会在场景里留下 `Missing (Mono Script)`，既得不到"只留美术"的目标，也继续制造"这是什么"的阅读干扰。因为 A 类场景已在 Build Settings 中禁用，此操作**纯属仓库卫生，不影响出包**——可以从容做，不需要赶。

**已核实的三处易误判**：

- **删 `Enemy_0Base.prefab` 是安全的（2026-09-15 实测）**：`EnemyCatalog.asset` 共引用 21 个 guid = **20 个 typed 敌人 prefab + `EnemyCatalog.cs` 自身**，**不含** `Enemy_0Base`、也不含两个 Test Variant。因此活敌人生成链路**完全未受影响**。
- **但删基座留下了两个孤儿**：`Enemy_Test-Ele.prefab` / `Enemy_Test-Fire.prefab` 是 `Enemy_0Base` 的 **Prefab Variant**，基座已删而 Variant 仍在 → Unity 中会表现为**断开继承的预制体**；它们只被已禁用的 `5BattleScene-Test1` 引用（实测），无任何活引用。→ **建议一并删除**（它们是已删基座的测试派生，且敌人属于玩法内容而非"要保留的美术"）。若确实想在那场景里当美术占位，须改为独立 prefab（Copy 而非 Variant），但没必要。
- **20 个 typed 敌人 prefab（`Enemy_GunTurret_*` / `Enemy_Mine_*` / `Enemy_Missile_*` / `Enemy_Patrol_*`）不是 `Enemy_0Base` 的 Variant**（实测 `m_SourcePrefab`）→ 全部保持完好。
- **gacha 代码的处置**：`Gacha_CoreOperation` / `Gacha_UIOperation` 既无资产挂载、也无代码引用；`Gacha_MainControl` 只挂在 `3GachaScene`。既然该场景只留美术、组件要摘除，"保留 gacha 代码"就等于**纯参考实现**。→ 建议移入隔离目录（如 `Assets/Legacy/Gacha/`）并附 README 标注「M2 抽卡参考实现，未迁移，不参与运行时」。**不要"封装"它**——封装意味着长期维护接口，对沉默的死代码是纯负担。

**场景移位（2026-09-15 用户批准：可以移动）**：四个禁用场景（`3GachaScene` / `4BattleScene` / `5BattleScene-Test0` / `5BattleScene-Test1`）可移入归档目录（如 `Assets/01_Scenes/Legacy/`）。依据：其实测场景名在代码与 AB 清单中**零引用**，且均 `enabled=0`；按 D25 场景名即 key 的约定，只要**不改名**就无副作用（移动只改路径，不改 key）。此为**可选**动作——记入 S5 一并处理即可。

### 5A.5 验证方式（本阶段的具体手段）

1. **GUID 挂载复核**（删任何脚本前必做）：取 `X.cs.meta` 的 guid，在全部 `.prefab` / `.unity` / `.asset` 中搜索该 guid。本次已验证可行，命令模板：

```powershell
cd Assets
$g = (Select-String -Path '路径\X.cs.meta' -Pattern '^guid:\s*([0-9a-f]{32})').Matches.Groups[1].Value
Get-ChildItem -Recurse -Include *.prefab,*.unity,*.asset -File |
  Where-Object { (Get-Content $_ -Raw -ErrorAction SilentlyContinue) -like "*$g*" } |
  Select-Object -ExpandProperty FullName
```

2. **回归基线**：以用户外发的 Demo 版本对应提交（`25fa21c1` 或试玩包所用提交）为**行为基线**，S4/S5 每个模块完成后按 §5A.3 的主链路清单人工过一遍
3. **静态检查**：硬编码资产路径扫描（本次已用）、asmdef 依赖方向检查（拆完后 `Tea.Game` 不允许引用 `Tea.Framework` 以外的框架层）

## 5B. P1B · 引擎升级阶段（排在 P1A 之后；原 P0B）

> **决策**（2026-09-15 用户确认）：**现在不切引擎**。P1A 先行；P1B 作为独立阶段排在 **P1A 之后、M2 内容扩张之前**，且**必须早于 P1C**（HybridCLR 的 il2cpp 补丁与 Unity 版本强绑定，先装再升等于把这份工作做两遍）。

### 5B.0 目标版本选择（依据，实测自 endoflife.date 2026-09-11）

| 版本 | 发布 | 安全支持 | 判断 |
|---|---|---|---|
| **2022.3 LTS（当前）** | 2023-05-30 | **已于 2025-05-07 结束**，无延长支持 | 已在维护窗口之外；最新版 `2022.3.62f3`（2025-10-28），本工程停在 `2022.3.60f1c1`（中国版） |
| 6.0 LTS | 2024-04-29 | **2026-10-16 到期（仅剩约一个月）** | 不选 |
| 6.2 | 2025-08-12 | 已于 2025-12-04 结束 | 不选 |
| **6.3 LTS** | 2025-12-04 | 2027-12-04（延长至 2028-12-04） | **目标**；最新 `6000.3.24f1`（2026-09-10） |

结论：升级目标是 **6.3 LTS**，不是 6.0，也不是最新的 6.6。

### 5B.1 为什么必须升级（不是"想升"）

1. **2022.3 已停止安全支持**（2025-05-07 结束）——引擎层面的漏洞修复与平台适配不再提供。
2. **Android 合规只会收紧**：Google Play 逐年提高 targetSdk 要求，旧引擎的支持上限会成为发布阻塞；本工程目标平台是 Android。
3. **热更线的兼容性风险同源**：§5 P0 要实测的"中国版 2022.3.60f1c1 与 HybridCLR 的兼容性"问题，本质就是引擎版本过旧的表现。
4. **越晚越贵**：当前是 M1 灰盒、159 个脚本、无线上内容；等到 M2/M3 内容堆起来再升，成本显著更高。

### 5B.2 本工程的迁移面（2026-09-15 实测）

**好的一面（比一般项目轻很多）**：

| 项 | 实测 | 结论 |
|---|---|---|
| Cinemachine `2.10.3` | 代码 **0 引用**、场景/预制体 **0 引用** | Cinemachine 3.x 的破坏性改名（`CinemachineVirtualCamera` → `CinemachineCamera`、命名空间变更）**零成本** |
| `com.unity.ai.navigation` `1.1.5` | 代码 **0 引用** | 1.x → 2.x 迁移**零成本** |
| 自定义渲染管线代码 | 全工程唯一挂在 Renderer 上的 RendererFeature 是 URP **内置**的 `ScreenSpaceAmbientOcclusion`（`Assets/ExampleAssets/Settings/UniversalRenderer.asset`） | **URP 17 的 Render Graph 改造几乎零成本**——没有自定义 Pass 需要重写 |

**坏的一面（两个真实风险）**：

1. **RealToon 是硬阻断点**。`Assets/RealToon/RealToon Shaders/Effects/DeNorSob Outline/` 下 `DepthNormalsFeature.cs` 与 `DeNorSobOutline.cs` 是自定义 RendererFeature，使用 **URP 12 之前就已废弃的 API**（`RenderTargetHandle`、`renderer.cameraColorTarget`）。RealToon **没有 asmdef** → 这些脚本编译进 `Assembly-CSharp` → **它们编不过等于整个工程编不过**。工程内 RealToon 为 **v5.0.8p7（2022-12）**，其 changelog 最高只到"URP 14 full support / Quick ready support for Unity 2023（测试用途）"，**仓库内无 Unity 6 / URP 17 支持证据**。
   - **用户已确认（2026-09-15）：RealToon 最新版本支持 Unity 6。** 因此风险从"不可用"降级为"**必须升级工程内的 RealToon 资产，并重新验证这两个 RendererFeature 在新版下的编译与运行**"。
   - 附带收益：升级 RealToon 后，这两个文件会被新版本覆盖/替换，旧 API 依赖自然消失。
2. **包清单与资产重序列化**：`textmeshpro 3.0.7` + `ugui 1.0.0` 在 Unity 6 变为 TMP 并入 ugui 2.0；URP / Cinemachine / ai.navigation 清单项全部变更。大版本升级会**重序列化几乎所有 `.prefab` / `.unity` / `.asset`**，加上 Android 侧 Gradle / AGP / NDK 版本变化——**刚补好的 `AndroidDemoBuilder.cs` 一键出包与已外发的试玩包基线都要重验**。

### 5B.3 为什么不是现在升（含反方论证）

**三个理由**：

1. **P1A 的工作与引擎版本无关**。读代码、定程序集边界（AOT/热更归属）、删死代码、去新旧纠缠——这些结论**在 2022.3 上做完可原样带到 Unity 6**，不会因之后升级而作废。
2. **升级 churn 会摧毁 P1A 的核心价值**。P1A 要的是"能读懂自己的 diff、能归因回归"；而换引擎会把整个仓库重序列化，届时又一次分不清"是我改的还是引擎改的"。
3. **降级风险**：若 RealToon 升级或 DHE/第三方插件在 Unity 6 上受阻，"先升"会直接卡死，P1A 一起停摆；而"P1A 先行"无论升级能否成立都能推进。

**反方论证（诚实记录）**：先升级的好处是"在最终引擎上只做一次 P1A"，并且全程可用实时 Editor 回路。这条成立——但它赌的是"RealToon 与所有第三方依赖在 Unity 6 上顺利可用"（未验证），而收益（编译回路）已可用远便宜的方式获得（见 §5A.3 方案 B/C、方案 A）。故仍推荐 P1A 先行。

### 5B.4 P1B 前置确认清单（开工前必须全部有结论）

- [ ] **Unity 6 发行版选择（新增，必须先定）**：Unity 6 **国际版** vs **Unity 6 中国版**。本工程现为 Unity 中国版 `2022.3.60f1c1`；本次调研发现的两个中国区相关问题（Unity CLI 被国区 CDN 重定向成老版本 `0.1.x`、中国版与第三方工具的兼容声明缺失）都指向"选国际版可减少一类不确定性"，但需确认账号/授权与下载渠道是否可用。**此决定影响后续所有工具链（CLI、HybridCLR、打包）。**
- [ ] **安装 Unity 6.3 LTS 时勾选模块**：Android Build Support（含 SDK/NDK）+ **Windows Build Support (IL2CPP)**（PC 验证链路必需；当前 2022.3 的 Standalone 后端是 Mono）
- [ ] **RealToon**：确认 Asset Store 上支持 Unity 6 / URP 17 的具体版本号；确认现有授权可升级；记录升级步骤与需要重新验证的材质/Shader 清单（工程内现为 `v5.0.8p7 / 2022-12`；用户已确认最新版支持 Unity 6）
- [ ] **Amplify Shader Editor**（`Assets/Plugins/AmplifyShaderEditor`，有独立 asmdef）：确认有支持 Unity 6 的版本；确认工程内自绘 Shader 是否依赖其特定版本行为
- [ ] **QFramework / ResKit / UIKit / SupportOldQF**：确认在 Unity 6 下可编译（QFramework 为纯 C#，风险低；ResKit 的 AB 与 Editor 工具需实测）

### 5B.5 P1B 步骤与退出条件

1. **隔离**：从 P1A 收尾提交拉出升级分支；先提交一次"升级前快照"（仅记录 `ProjectVersion.txt` 等）
2. **升级第三方插件**：RealToon → ASE → DOTween → TMP 字体，逐个升级并单独提交，每步记录编译状态
3. **升级引擎**：用 Unity Hub 安装 6.3 LTS（`6000.3.x`），打开工程触发资产重序列化；**这一步单独一次提交，纯 churn，不含任何业务改动**
4. **修编译错误**：按错误逐条处理；重点看 `Assembly-CSharp`（RealToon 等无 asmdef 的第三方脚本在此）
5. **渲染回归**：URP 14 → 17 后逐场景截图对比（角色着色 / 描边 / 后处理 / 粒子 / UI），重点验证 RealToon 的 `DeNorSob Outline` 与 `DepthNormals`
6. **Android 重出包**：跑一遍 `Thrud/Demo/Android/` 一键构建，按 `../01_里程碑与执行/15…真机验收清单` 重验
7. **同步文档**：`AGENTS.md` 的项目事实段（Unity 版本、'不是 Unity 6' 的约束）、01 架构文档、02 热更方案、本文 §1 与 §5 的版本相关结论
8. **退出条件**：主链路（ConfigScene → Login → 2MainScene → 选关 → 编队 → 战斗 → 结算 → 返回）Play 全绿；Android 真机包可安装可玩且无渲染异常；`AGENTS.md` 版本事实已更新；升级提交与业务提交分离且可整体回退

### 5B.6 P1B 风险

| **`link.xml` 被覆盖** | 低 | HybridCLR 自动生成的 link.xml 若指向 `Assets/link.xml` 会覆盖现有裁剪保护 | `outputLinkFile` 指向独立路径 |
| **Windows 与 Android 清单不一致** | 中 | 平台相关 AB 名/依赖差异 | 构建输出按平台隔离；服务器目录按 `Channel/平台` 分子目录（02 文档既有结论） |
| **热更后旧存档不兼容** | 中 | 数据结构变更 | 存档版本号 + 迁移脚本（`04_外围系统设计`） |
