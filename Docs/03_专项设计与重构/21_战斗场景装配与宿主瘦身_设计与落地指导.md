# 战斗场景装配与宿主瘦身：设计与落地指导

> 产出日期：**2026-09-19**。
> 定位：`Assets/02_Scripts/03_Battle/BattleSceneRuntimeHost.cs`（**559 行**）的职责收拢方案。
> 来源：用户提问——「`playerControl` 不再被持有，相应内容通过 System 驱动 Actor 自行访问获取后交互；host 仅作为 tick 触发器、不承担逻辑内容」，以及随之的两轮评审结论。
> 关系：本文是 **19 文档（表现层分层）的延续与贯彻**，不是替代。Actor/View 的通道规则、`BindableProperty` 纪律仍以 19 与 `02_系统与玩法设计/01_技术架构设计.md` 为准；本文只解决「装配与调度放在哪里」。

## 0. 结论摘要

| 结论 | 项 |
|---|---|
| ✅ **同意做（5 步）** | ① 宿主不再缓存 `playerControl` 副本；② 搬走编队/关卡数据管道与诊断；③ Actor `Tick(dt)` 内聚中间量；④ 抽独立装配器 `BattleSceneAssembler`；⑤ 最小引用注入（19 §6 的"步骤 6"） |
| ❌ **不同意做（3 条）** | ① 让 System 构造/查找 Actor（回退"System 脱 View"）；② 让 System/Actor 自行访问 `Battle_PlayerControl`（把 rig 升级为**服务定位器**）；③ 把每帧相位顺序改为 System 间的隐式约定 |
| 🎯 **目标** | 宿主收敛到 **100–150 行**，只保留「场景生命周期 + 装配调用 + 相位表」三类职责 |

**一句话判据（本方案的总纲）**：

> **宿主可以薄，但不能空。** 组合根（装配）、场景生命周期（owner）、相位表（SystemGroup 集成点）必须由场景级对象持有；**其余一切都应该搬走**。判断某段代码该不该留在宿主，只问一句：**「它是否只在场景装配/卸载时才需要存在？」** 是 → 留；否 → 搬。

## 2. 评估：哪些建议成立、哪些不成立

### 2.1 成立的（4 条）

| # | 建议 | 为什么成立 |
|---|---|---|
| 1 | **宿主不再运行期持有 rig 副本** | Model 已是唯一真相（§1.3）；同时消除"装配期用字段、运行期用 Model"的**双路径**。 |
| 2 | **搬走编队/关卡数据管道与诊断** | 150 行纯数据逻辑零帧依赖，放在 MonoBehaviour 里没有测试面、改一次要重新过 Play。 |
| 3 | **宿主不做表现编排** | 现在 `TickActors()` 在替 Actor 算 `freePoint`/`target`/`rotation`（486–503），这是"宿主里长出表现逻辑"。 |
| 4 | **装配抽成独立类** | 宿主同时承担"生命周期 + 装配 + 调度 + 数据 + UI + 销毁"六件事，改任一都要读全文件。 |

### 2.2 不成立的（3 条，附反例）

| # | 建议 | 反例与理由 |
|---|---|---|
| 1 | **让 System 构造/查找 Actor，实现"System 驱动 Actor 自行访问"** | **生命周期不匹配**：`BattleArchitecture` 是应用级常驻单例（宿主 `185` 行注释"架构常驻跨场景"），System 的生命周期是**架构级**；Actor 持有场景里的 `Transform`/`Rigidbody`，生命周期是**场景级**。System **结构上无法承担场景级释放**。<br>**并且是回退**：`BattleRoleSystem` 的 `actor` 字段、`AttachActor`/`DetachActor`、`BattleMovementSystem` 的 actor 字段，**正是 2026-09-19 第 1 步刚删掉的**（见 19 文档）。让 System 自己 `FindObjectOfType` 则是引入**隐式查找**：启动顺序、多实例、prefab 变体都会静默失败。 |
| 2 | **让 System/Actor「自行访问获取」rig 的字段** | `Battle_PlayerControl` 不是服务，是**场景引用总仓库**（约 30 个序列化字段：相机、双轴、挂点、子弹 prefab…）。让 N 个消费者各自去拿，等于把它升级为**服务定位器**：依赖从"宿主 1 处显式"扩散成"运行期 N 处隐式"。这与 19 §6「最小引用注入」**方向相反**——那里要的是让 System **不再依赖这个类型**。 |
| 3 | **host 仅作 tick 触发器（丢掉顺序）** | 现有顺序有硬依赖：`TickActors()` 必须在 `BattleWeaponSystem.Tick()` **之前**（后者每帧写 `FreeAimRotation`/`ActiveElement` 并在同一方法内 `PressTrigger()` 开火）；`PublishAmmo` 卡在两者之间；`Aim.TickLateUpdate()` 必须在 `Battle_MainPanel.TickForBattle` 之前。**顺序是逻辑，不是样板。**<br>丢掉它只会退化成两种更糟的形态：System 之间的隐式假设，或 `[DefaultExecutionOrder]`（System 不是 MonoBehaviour，**挂不上**）。 |

> **正确命名**：宿主的 `Update/FixedUpdate/LateUpdate` 是这套架构的 **SystemGroup / PlayerLoop 集成点**（等价于 ECS 的 `SystemGroup` + `UpdateBefore/After`）。给它命名，它就不是"堆积"，而是一项有名有姓的职责。

### 2.3 一处必须明说的取舍：Actor 不读 Model 的纪律要开受控例外

`BattleMovementActor` 类注释写着"**不读取战斗 Model**"，这是好纪律。第 3 步让它内聚 `target`/`freePoint` 会碰这条线，因此约定：

- ✅ **允许**：构造期注入它该有的依赖（相机 `Transform`、锁敌提供者/Model 引用），运行期只读。
- ❌ **禁止**：运行期通过 `Architecture.Interface`、`FindObjectOfType`、静态全局去**查找**依赖。

即：**依赖注入可以，服务定位不行。** Actor 的依赖集合必须能从它的构造函数一眼看全。

## 3. 目标形状（命名定稿）

```
BattleSceneRuntimeHost (MonoBehaviour, 目标 100–150 行)      ← 场景唯一调度节点
  ├─ 场景生命周期：Awake（发布 rig 到 Model）/ Start / OnDestroy（释放）
  ├─ 调一次装配器：assembler.Build()
  └─ 三相位调度表：Update / FixedUpdate / LateUpdate（顺序集中一处 + 注释说明依赖）

BattleSceneAssembler (普通类, ~150 行, 新建)                 ← 组合根，从宿主搬出
  ├─ 构造 4 个 Actor（Movement/Role/Weapon/Camera）
  ├─ 调各 System.Initialize / ResetForBattle / StartLevel
  ├─ 发布元素子弹、执行出生点传送
  └─ 对外只读暴露 4 个 Actor 供宿主 tick

BattleSetupSystem (AbstractSystem, ~200 行, 新建)             ← 从宿主搬出 150 行 + 关卡解析
  ├─ TryResolveLevel(sceneName) / ResolveBattleDatas() / ResolveTeamCatalog()
  ├─ 编辑期直读回落（#if UNITY_EDITOR 保留）/ 正式构建失败回退 BattleSceneGate
  └─ ⚠️ 只解析数据、返回结果；不驱动任何 View（stageDirector.Setup 仍由宿主做）

BattleRoleActor.Tick(dt) / BattleWeaponActor.Tick(dt)         ← 中间量内聚（依赖构造期注入）
BattleUiSystem 或 BattleUiLauncher(MB)                        ← 面板开启协程（协程必须有 MB）
```

**命名说明**：原提议 `BattleBattleAssembly` 有重复词，改为 **`BattleSceneAssembler`**——无重复、作用域明确（本场战斗的装配）、与既有 `BattleTeamRuntimeBuilder` / `BattleSceneGate` / `BattleSceneRuntimeHost` 同族。备选：`BattleRuntimeAssembler`。

**归属与依赖方向**：`BattleSceneAssembler` 与 `BattleSetupSystem` 都在 `TeaGame.Battle`（`03_Battle/`），**不新增程序集、不新增契约层类型**。`BattleSetupSystem` 需在 `BattleArchitecture.cs` 注册（System 数 9 → 10）。

## 4. 落地路线（5 步，一步一提交、每步可停）

> **每步统一验收口径**（与 19 文档一致）：

### 步骤 1 —— 宿主不再持有 `playerControl` 副本（低风险，建议先做）

**范围**：`BattleSceneRuntimeHost.cs`（32 行访问点中的运行期部分）、`BattleRoleSystem.cs:57`。

**改动**：
1. 保留 `[SerializeField] private Battle_PlayerControl playerControl;`（**场景绑定输入，不能删**）。
2. `Awake` 首行把它发布进 Model：`StateModel.Controller = playerControl;` → **Model 成为唯一运行期持有者**。
3. 新增一个只读属性做桥接，避免一次性重写 32 行：`private Battle_PlayerControl Rig => StateModel.Controller;`，文件内 `playerControl.X` → `Rig.X`。
4. **删除** `BattleRoleSystem.cs:57` 的 `State.Controller = controller;`（改为不再写入；参数暂时保留，第 5 步再收窄），使写入者唯一。
5. `OnDestroy` 的 `if (StateModel.Controller == playerControl) StateModel.Controller = null;` 改为 `== Rig`。

**唯一行为差异（必须验证）**：`State.Controller` 的赋值时机从 **Start** 提前到 **Awake**。Awake→Start 之间若有代码读它，以前是 `null`、现在是 rig。已核实的读者（`BattleCameraSystem`/`BattleWeaponSystem`/`BattleAimSystem`/`BattleLevelFlow`/`BattleSkillSystem`）都受 `battleReady` 或事件驱动，不在这段窗口内运行；但**必须靠编译 + Play 复核**，不要凭推理放过。

**验收**：
- 静态：`Select-String 'playerControl' BattleSceneRuntimeHost.cs` 只剩**声明 1 行**；`BattleRoleSystem.cs` 无 `State.Controller =`。
- Play：进战斗后**移动 / 相机 / 瞄准 / 开火 / 换弹 / 技能 / 暂停全部正常**（即"装配链没有因为提前赋值而改变行为"）。

## 5. 新增纪律（建议并入 19 文档与 `01_技术架构设计.md`）

1. **宿主判据**：「它是否只在场景装配/卸载时才需要存在？」是 → 留宿主；否 → 搬走。
2. **宿主三职责**：组合根（装配） / 场景生命周期（owner） / 相位表（SystemGroup）。**只此三类**。
3. **装配器不 tick、不持生命周期**；调度顺序只在宿主一处，且带注释说明依赖关系。
4. **Actor 依赖**：构造期注入（可），运行期查找（禁）。Actor 的依赖集合必须能从构造函数一眼看全。
5. **System 不驱动 View**：System 可以解析数据并返回结果；把结果交给 View/Actor 的动作由宿主或装配器做。
6. **`BindableProperty` 通道判据**（源自 19）：值每帧都写且消费方必须每帧用一次 → 是**命令**，走显式 tick；否则才是**状态**，可绑定。（其 setter 对"值未变"直接 return，`QFramework.cs:717`。）

## 6. 顺带回答代码里遗留的两个疑问

### 6.1 `host:34`「rig 为什么是手动拖拽的？希望能自动查找，没有就呼叫热更创建」

可以做，但**不要用 `FindObjectOfType` / `GetComponentInChildren`**（隐式、顺序敏感、多实例/变体会中招）。正规做法是**显式解析 + 明确失败路径**，落在 `BattleSceneAssembler`：

1. 优先读宿主上的序列化引用（保持现状，编辑器期零成本）；
2. 为空 → 读场景注册组件（例如 `SceneAnchor` / 一个 `BattleSceneRefs`）；
3. 仍为空 → `ResKit` 异步加载 rig prefab 并实例化（这就是"呼叫热更模块"的正确形态：走既有 AB 管线，而不是 `Resources.Load`）；
4. 全部失败 → 走 `BattleSceneGate.TransitionTo(BattleTeamSession.ReturnSceneName)` 并给明确日志（参考 `ResolveBattleDatas` 的失败文案风格）。
