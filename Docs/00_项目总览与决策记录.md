# 项目总览与决策记录

> 本文档是 THRUD 重制项目（Thrud-Remake）的总纲。它记录项目定位、经过多轮对话确认的开发方向，以及各方案文档的索引。其余文档编号见下文的文档地图。

## 项目定位

本项目是以手游《斯露德》（THRUD）为蓝本的 Unity 个人重制工程。原游戏由 B 站旗下 Access! 工作室开发，2023 年 8 月 17 日公测，2024 年 10 月 9 日停运。重制的目标不是复刻运营系统，而是以现代工程结构重新实现其核心玩法——全 3D 空域、四角色切换、锁定射击与元素机制——并在 QFramework 架构与热更新体系下保持长期可迭代。

工程当前状态的完整盘点见各方案文档；一句话概括现状：**新旧两套代码双轨并行、QFramework 只使用了核心架构、热更新空白、美术资源充足但组织混乱**。本次重制将保留美术资产与旧代码中的可参考逻辑，重建代码结构。

## 目标与非目标

目标：

- 基于 QFramework 建立分层、模块独立的架构，彻底消除新旧代码双轨并行的混乱
- 引入 HybridCLR 代码热更与 YooAsset 资源热更，并支持本地模拟更新流程
- 核心战斗闭环（编队 → 进战斗 → 锁定射击 → 切人 → 元素 → 结算）优先成型
- 单人开发节奏：先逻辑与大方向玩法，后美术与细节；灰盒优先
- 内置数据埋点与日志落盘，便于测试期问题收集与数值复盘
- 网络接口抽象层保留，为后续 P2P 联机预留扩展点（本期不做联机功能）

非目标（本期明确不做）：

- 不做账号系统、服务器后端、真实运营环境（登录为本地流程占位）
- 不做完整商业化数值体系（如赛季通行证、多档付费礼包）
- 不做 P2P 联机实装（只做接口预留）
- 不排硬性工期（开发时间不定），只排任务依赖顺序

## 版权与边界声明

本工程使用原版游戏的拆包美术资产（模型、贴图、动画）用于个人学习与开发。**若未来计划公开发布，需评估并替换全部受版权保护的资源**（灰盒策略为此预留了平滑替换路径：所有美术资产走 YooAsset 资源层，替换不触碰代码）。本方案不讨论商业化分发。

## 决策记录

以下为多轮对话确认的方向性决策。编号 D01 起，作为后续文档的引用依据。

| 编号 | 决策项 | 结论 | 理由 |
|------|--------|------|------|
| D01 | 平台与网络形态 | PC + Android 双端，本地单机；保留网络接口抽象 | 单人开发砍掉后端工作量；P2P 后续补充 |
| D02 | 热更新路线 | HybridCLR（代码热更）+ YooAsset（资源热更） | 全 C# 开发，无需 Lua 胶水层；YooAsset 资源管线成熟 |
| D03 | 现有代码处理 | 保留美术资产与参考逻辑，重建代码 | 新旧双轨是最大混乱源，桥接层长期共存不可持续 |
| D04 | MVP 范围 | 核心战斗闭环优先 | 单人开发先验证手感；原版因反复改核心玩法而失控，以此为戒 |
| D05 | 飞行形态 | 全 3D 空域开放战斗（含上下轴） | 还原原版最终形态；输入层已预留 MoveDepth 轴 |
| D06 | 锁定手感 | 默认半自动锁定（待最终确认） | 准星吸附 + 目标切换，可复用现有 BattleAimSystem；备选方案见玩法文档 |
| D07 | 元素机制 | 架构支持附着/相变，首版内容为克制 + 独立状态 | 避免原版类原神反应链的数值失控；保留升级空间 |
| D08 | 主城形态 | 2D 功能页 | 沉浸 3D 主城投入大，2D 页先支撑功能循环，后续可升级 |
| D09 | 养成深度 | 三线轻量：角色等级/升星、武器等级/突破、简化符灵 | 支撑"刷关 → 变强 → 过更难关"循环，量可控 |
| D10 | 内容量 | 精而少：3-4 普通敌人 + 1 精英 + 1 Boss；清剿/护送/防守；3-5 关 | 先验证战斗策略层成立，再扩内容 |
| D11 | 美术策略 | 灰盒优先，玩法定稿后接入正式资产 | 专注逻辑与手感；正式资产走资源层可平滑替换 |
| D12 | 抽卡 | 第二里程碑，与主城功能页一起 | 依赖背包/存档数据层，不宜占用 MVP 时间 |
| D13 | 排期方式 | 不排硬工期，只排任务依赖顺序 | 开发时间不定 |
| D14 | 埋点与日志 | 内置 Telemetry 模块：数据埋点 + 分级日志落盘 | 便于测试期问题收集与数值复盘（用户补充需求） |
| D15 | 常驻管理场景 | 新建 ConfigScene 独立承载配置与场景切换，作为应用入口与常驻层 | 配置与玩法场景解耦，切场景不销毁管理器 |
| D16 | 存在检查语义 | "检查是否已加载"（懒加载守卫，防重复 + 编辑器兜底） | 明确启动守卫的实现逻辑 |
| D17 | 管理场景职责 | 配置对象 + 场景切换控制器（SceneFlow），不吞全局系统 | 避免管理场景膨胀 |
| D18 | 旧单例去留 | StoreBattleRoleData / BattleRoleRepository 迁入 ConfigScene，去 DontDestroyOnLoad | 避免双重常驻重复实例 |
| D19 | 场景来源 | 先 Build Settings，热更接入后切 YooAsset 场景分组 | 现阶段最简单稳妥 |
| D20 | 切换策略 | 卸载旧玩法场景，ConfigScene 永驻 | 内存干净，场景栈不堆积 |
| D21 | Loading 遮罩 | LoadingGroup 预制件并入 ConfigScene 作全局遮罩 | 复用现有资源，替代运行时实例化 |
| D22 | UIRoot 归属 | 放管理场景（跨场景常驻） | 与 UIKit 接入方式一致 |
| D23 | 实施节奏 | 先固化文档，后续按依赖顺序实施 | 与现有"文档驱动"流程一致 |
| D24 | 场景引用方式 | SceneRefTable SO：GUID 锚定场景资产，路径由编辑器自动同步；场景名称/路径不写死（用户需求） | 场景重命名/移动后零代码改动；保留枚举作逻辑 ID 与文件名解耦 |
