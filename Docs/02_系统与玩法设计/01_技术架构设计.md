# 技术架构设计

> 本文档定义重制工程的总体架构：QFramework 的使用方式、程序集划分、模块边界、目录规范与网络抽象层。它是后续所有实现工作的骨架。

## 架构分层

工程按四层组织，自下而上：

```
┌─────────────────────────────────────────────┐
│ 游戏模块层  Login / MainCity / Gacha /      │
│            Battle / Grow / Bag / Task       │   ← 全部在热更程序集
├─────────────────────────────────────────────┤
│ 框架层     QFramework(Arch/UIKit/AudioKit)  │
│            通用工具(对象池/事件/日志/埋点)    │   ← AOT 主程序集
├─────────────────────────────────────────────┤
│ 基础设施层 HybridCLR / YooAsset / Unity引擎  │   ← 插件与引擎
├─────────────────────────────────────────────┤
│ 数据层     配置表 / 存档 / 埋点队列 / 版本    │   ← 横跨各层
└─────────────────────────────────────────────┘
```

- 上层依赖下层，下层不感知上层。模块间不得互相 `using`，通信走 QFramework 事件与数据层。
- 数据层被各层共享：配置表驱动内容，存档驱动进度，版本信息驱动热更流程。

### QFramework 各组件在本工程中的角色

| QFramework 组件 | 用途 | 说明 |
|-----------------|------|------|
| Architecture / Model / System / Command / Event | 模块内逻辑骨架 | 现有 `BattleArchitecture` 模式推广到全部模块 |
| UIKit | UI 面板生命周期管理 | 接入后 UI 代码自动生成绑定，支持面板栈与资源热更 |
| AudioKit | 音效/音乐播放 | 封装对象池与音量控制 |
| ActionKit | 异步时序（可选用） | 过场、演出、连招序列 |
| ResKit 的 AB 方案 | 弃用 | 资源热更统一走 YooAsset；ResKit 中加密/MD5 等工具按需迁移 |

每个游戏模块（如战斗、抽卡）拥有自己的 `Architecture` 子类（`BattleArchitecture` 已存在），内部注册本模块的 Model 与 System。跨模块共享状态放在全局 `GameModel`，通过全局事件广播变化。

### 表现层（View / Actor）分层

> **2026-09-19 用户确认并落地，编译/Play 待验**。完整入口与验收见 `../03_专项设计与重构/19_表现层分层_View与Actor_设计.md` 当前实施记录。

| 通道 | 做法 |
|---|---|
| UI 状态及准星目标位置 | Model 的 BindableProperty → View 注册即读；坐标转换、Lerp 与控件赋值归 View |
| 移动/传送 | System 计算规则与力度 → MovementActor 执行刚体操作；允许位置/速度只读反馈 |
| 角色/武器/相机表现 | 对应 Actor 提供语义方法，持有具体组件与插值缓存；不读取全局 Model、不决定玩法 |

- `battle_runtime` 统一装配和帧序；Actor 为场景内普通 C# 对象，离场解除引用，不另建程序集。
- System 不访问 UI 字段或 Animator；InputSystem 保持不变，CameraSystem 现有视角控制保留。
- 准星目标用 `BindableProperty<Vector2>`，框架已有快速比较器；基础数值使用 int/float，不引入自定义 struct/全局 Comparer 修改。
- 本次只做玩家，敌人留待后续确认，子弹与高频池对象不增加 Actor。

### 场景装配与宿主职责（2026-09-19 用户确认并落地）

> 来源：`../03_专项设计与重构/21_战斗场景装配与宿主瘦身_设计与落地指导.md`（含实测诊断、被否决的三条提案及反例、逐步验收口径）。
> 本节是**"某段代码该不该留在这个类里"的通用判定口径**，不限于战斗场景；落地记录见该文档 §8。

**宿主判据（唯一一条）**：「这段代码是否只在场景装配/卸载时才需要存在？」是 → 留场景宿主；否 → 搬走。

| # | 纪律 | 落地形态（战斗场景实测） |
|---|---|---|
| 1 | 宿主只承担**三类**职责：场景生命周期（owner）/ 组合根调用 / 相位表（SystemGroup 集成点） | `BattleSceneRuntimeHost` = `Awake`（发布 rig 进 Model）+ 一次装配调用 + `Update/FixedUpdate/LateUpdate` 相位表 + `OnDestroy` 释放；559 → 314 行后无一项该搬而未搬 |
| 2 | 装配抽成**独立组合根**：不 tick、不持生命周期、不读 `Update` | `BattleSceneAssembler.Build(...)` 只跑一次；顺序依赖靠"宿主在 `Start` 里调用"表达，**不用协程/延时掩盖** |
| 3 | 数据解析进 System，**System 不驱动 View/流程** | `BattleSetupSystem` 只解析数据并返回结果（含 `RetreatToEntryScene` 失败标志）；出生点传送、`Director` 注入、回退入口场景由宿主/装配器执行 |
| 4 | Actor/View 依赖**构造期注入**，禁止运行期查找 | 依赖集合必须能从构造函数一眼看全；`Architecture.Interface` / `FindObjectOfType` / 静态全局**只允许用于事件总线**，不得用于取依赖 |
| 5 | 每帧相位顺序只在宿主**一处**，且必须写注释说明依赖 | `Update/FixedUpdate/LateUpdate` 就是本架构的 SystemGroup；顺序即逻辑（例：表现 tick 必须先于武器 tick——后者在同一方法内开火） |

**同批确认的三条附带口径**：

- **参数 vs 依赖**：单帧内的**值**（速度、冲刺标记、`dt`）作为参数传入是正常的；只有**派生中间量**（锁定目标点、回正点、朝向）才下沉到 Actor/View。
- **命令 vs 状态**：每帧都写、且消费方必须每帧用一次的量 → 是**命令**，走显式 tick；否则才是**状态**，可用 `BindableProperty`（其 setter 对"值未变"直接 return，承载不了每帧命令）。
- **场景对象的字段由它自己写**：System 需要改变场景对象（rig 等）的字段时**发事件请求**，由该对象在自己的回调里写。例：`BattleEvent_ControlTakeOverRequested` → `Battle_PlayerControl` 写 `ControlTakeOff`（该字段同时被出生动画 Timeline 驱动，因此必须留在 rig 上、保持唯一状态）。

## 程序集划分

程序集划分直接服务于热更新目标（细节见 `02_热更新方案.md`）：

| 程序集 | 内容 | 归属 | 说明 |
|--------|------|------|------|
| `QFramework` | QFramework 框架本体 | AOT | 稳定，不进热更 |
| `Tea.Framework` | 框架层：对象池、事件、日志、埋点、网络抽象、通用组件 | AOT | 稳定，不进热更 |
| `Tea.Game` | 全部玩法模块：战斗、主城、抽卡、养成、UI | **热更** | 迭代最频繁，全量进热更 DLL |
| `Tea.Data` | 配置加载、存档读写、数据结构 | 热更 | 随内容频繁变更 |
| `Tea.EditorTools` | 编辑器工具（配置表编辑器、打包工具） | 编辑器专用 | 不进运行时包 |

热更程序集的代码全部放在 `Assets/Game/` 下并通过 `.asmdef` 隔离；AOT 框架代码放在 `Assets/Engine/` 下。HybridCLR 的补充元数据（AOT 泛型）在构建时自动生成。

命名规范：

- 命名空间与目录一一对应：`TeaGame.Battle` → `Assets/Game/Modules/Battle/`

- 类型命名：System 以行为动词命名（`BattleRoleSystem`）、Model 以状态名词命名（`BattleStateModel`）、事件以过去式/完成态命名（`BattleRoleSwitchedEvent`）

## 场景与流程编排（多场景常驻模式）

> 本工程采用**常驻管理场景**架构（决策 D15-D23，详见 `08_常驻管理场景_ConfigScene_设计.md`）：`ConfigScene` 为应用入口与常驻层，所有玩法场景以 additive 方式叠加在其上切换，切换由 ConfigScene 内的 SceneFlow 统一控制。

```
Build Settings:
[0] ConfigScene      ← 入口，常驻，永不卸载（承载 GameRoot/SceneFlow/UIRoot/LoadingGroup/全局配置）
[1] LoginScene       ← additive
[2] MainScene        ← additive（主城 2D 功能页）
[3] GachaScene       ← additive
[4] BattleScene      ← additive
[5] BattleGraybox    ← additive（灰盒测试盒）
```

启动流程：

```
App 启动（ConfigScene）
 ├─ AppBootstrapper：日志/埋点 → 全局配置 → 全局架构 → SceneFlow 初始化
 ├─ SceneFlow.RequestLoad(Login)（additive）
 └─ 后续所有切换均走 SceneFlow（卸载旧玩法场景 + 加载新玩法场景）
```

- **懒加载守卫**：ConfigSceneGuard 检查管理场景是否已加载（`SceneManager.GetSceneByName(...).IsValid()`），未加载则 additive 加载（编辑器直接 Play 玩法场景时自动兜底）
- **切换纪律**：禁止单场景 `LoadScene`（会卸载 ConfigScene）；统一 `SceneFlow.RequestLoad` + additive + active scene 管理
- **跨场景参数**：`SceneRequest.Payload` 请求对象模式，目标场景通过 `SceneFlow.GetPayload<T>()` 读取
- **旧单例迁移**：`StoreBattleRoleData` / `BattleRoleRepository` / `LoadingGroup` 迁入 ConfigScene，移除 DontDestroyOnLoad
- **UI 常驻**：UIRoot 放 ConfigScene，模块 UI 面板叠加其上跨场景常驻

原单场景链路（`0Login → 1Main → 2Gacha → 3Battle`）将被 additive 模式取代，作为过渡期兼容保留。

## 模块边界与通信

模块独立性是本工程"合理"标准的核心要求。约束如下：

- 每个模块自带入口 `IXxxModule`，只暴露 Init / Shutdown / 对外命令，不暴露内部类
- 模块内状态在模块内 Model 中；跨模块数据一律经全局 `GameModel` 或存档读写
- 模块间通信使用 QFramework 全局事件（如 `BattleEnteredEvent`、`GachaResultEvent`、`BagItemChangedEvent`），消费者在事件表集中登记
- 任何模块不得 `new` 另一个模块的 System/Model，统一通过各自 Architecture 获取
- 共享工具（对象池、日志、埋点）归框架层，模块只调用不实现

事件表示例（后续在实现中维护成独立文件）：

| 事件 | 方向 | 触发方 → 消费方 |
|------|------|-----------------|
| `BattleEnteredEvent` | 主城 → 战斗 | 携带关卡 ID 与编队数据 |
| `BattleSettledEvent` | 战斗 → 主城/养成 | 携带评价、掉落、用时 |
| `BagItemChangedEvent` | 养成/抽卡 → 背包 UI | 携带变更的物品与数量 |
| `HeroUnlockedEvent` | 抽卡 → 编队/图鉴 | 携带角色 ID |

## 网络抽象层（P2P 预留）

本期为纯本地单机，但接口层现在就搭好，避免日后联机改造伤筋动骨：

```csharp
public interface INetworkService
{
    void Connect(ConnectOptions options, Action<bool> onResult);
    void Disconnect();
    bool IsConnected { get; }
}

public interface IRealtimeService   // 供 P2P 联机使用
{
    void CreateRoom(RoomConfig config, Action<RoomResult> onResult);
    void JoinRoom(string roomId, Action<RoomResult> onResult);
    void SendReliable(int channel, byte[] payload);
    void OnReceive(Action<int, byte[]> handler);
}

public interface IBattleSnapshot   // 战斗状态序列化点，供联机同步
{
    byte[] SerializeFrame(int frameIndex);
    void   RestoreFrame(byte[] snapshot);
}
```

- 当前提供 `LocalNetworkService`（本地占位实现），后续可替换为 Steam P2P、自研 UDP 或第三方联机 SDK，替换点仅在框架层
- 战斗的联机同步策略（预测/回滚、帧同步 vs 状态同步）不在本期范围内，但 `IBattleSnapshot` 要求战斗逻辑在关键状态处具备可序列化能力，实现时注意避免把 Unity 对象直接塞进快照

## 编码与工程纪律

- 代码注释与提交信息使用中文
- 模块内不允许出现 `Instantiate/Destroy` 的高频调用路径（见性能文档，统一走对象池）
- 不允许模块间 `using`；跨模块引用触发 Code Review（单人开发时以搜索检查代替）
- 配置数据不允许硬编码在类中（伤害、CD、掉落等一律进配置表）
- 热更程序集内禁止使用 `UnityEditor` API；编辑器工具单独放 `Tea.EditorTools`
