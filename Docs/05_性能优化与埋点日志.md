# 性能优化与埋点日志

> 本文档定义工程的两个横向支撑模块：性能优化策略（对象池、渲染、GC、加载）与 Telemetry（数据埋点 + 分级日志落盘，决策 D14）。它们不归属任何业务模块，由框架层提供，全体模块共用。

## 性能目标

| 场景 | 目标值 | 备注 |
|------|--------|------|
| PC 战斗帧率 | 1080p 稳定 60fps | 开发基准机 |
| 中端安卓战斗帧率 | 45fps+，稳定不掉到 30 以下 | 首版优化基准 |
| 战斗场景加载 | 进图到可操作 ≤ 3s | 首包资源优先，其余异步 |
| 启动到主城 | ≤ 10s（含热更检查） | 首包内资源不全加载 |
| 战斗内关键路径 GC | 0 分配/帧 | 对象池 + 缓存 + 免闭包 |

## 运行时优化

### 对象池（最高优先级）

现状痛点：旧武器代码对每发子弹执行 `Object.Instantiate` + `Object.Destroy`，敌人、伤害飘字、特效同理，GC 压力集中在战斗高频路径。

统一方案：框架层 `ObjectPool<T>`（复用现有 QFramework 对象池概念或自行实现），覆盖以下对象类型：

| 对象 | 池容量建议 | 说明 |
|------|-----------|------|
| 子弹 | 每武器 64-128 | 弹道命中后回收 |
| 敌人 | 单屏上限 20 + 缓冲 | 出屏/死亡延迟回收，避免频繁实例化 |
| 伤害飘字 | 64 | 文本复用，减少 TMP 重建 |
| 弹壳/命中特效 | 128 | 带自动回收计时器 |
| 敌人弹幕 | 128 | 同子弹 |

纪律：模块代码禁止直接 `Instantiate`/`Destroy` 高频对象，统一走 `PoolSystem`。对象池容量与预热时机（关卡加载时预热）进配置。

### 渲染优化（URP）

- URP 分级画质：PC 高档（阴影 2K 级联、后处理全开）/ 安卓中档（阴影距离收紧、后处理按需）/ 低档（关阴影、降分辨率缩放）
- 合批：静态合批 + GPU Instancing（子弹、小怪、建筑）；UI 图集合并，避免零散小图
- 材质：同角色同材质实例合并；灰盒阶段就按"未来要替换成正式资产"的规范组织材质
- LOD：角色/场景模型按需生成 LOD 组（`Art/Characters` 已有高模，构建管线统一生成）
- 特效：粒子系统控制最大粒子数；避免透明叠加过多导致 overdraw

### 物理与判定

- 子弹命中优先用 `Physics.Overlap*` 与射线，不依赖 Rigidbody 逐帧移动（可选方案：自研弹道组件）
- 敌人 AI 状态机低频更新（分帧调度，每帧只更新部分敌人）
- 触发器数量控制，碰撞矩阵按层过滤（玩家层/敌人层/子弹层/场景层）

### GC 纪律

- 战斗内 Update/FixedUpdate 路径禁止：LINQ 分配、闭包捕获、字符串拼接、每帧 `GetComponent`
- 缓存：`GetComponent` 结果缓存到字段；`Find*` 只在初始化用
- 动画参数名用 `Animator.StringToHash` 预缓存
- 每版本在 Android 真机跑一次 Profile 采样，记录峰值分配，作为验收门槛之一

## 加载优化（YooAsset）

- 资源按模块分组（见热更方案），按需加载，不整包预加载
- 关卡加载：进图前预加载该关资源清单 → 进度条等待 → 场景激活；异步分帧，避免主线程卡顿
- 图集/字体等公共资源：首包内置，常驻内存（引用计数管理）
- 资源卸载：`UIResource` 生命周期由 UIKit 面板管理，场景资源由场景流程控制器管理，杜绝"加载后永不卸载"

## 数据埋点与日志

### 分级日志

| 级别 | 用途 | 落盘 | 说明 |
|------|------|------|------|
| Debug | 开发细节 | 仅编辑器 | 不写文件 |
| Info | 流程节点（进入战斗、结算、热更） | 写文件 | 滚动覆盖（保留最近 N 个文件） |
| Warn | 异常状态（配置缺失、加载失败重试） | 写文件 | 触发埋点 |
| Error | 可恢复错误 | 写文件 + 弹提示 | 触发埋点 |
| Fatal | 崩溃前状态 | 立即 flush | 配合全局异常捕获 |

- 日志文件：`PersistentDataPath/log/`，按日滚动，启动时压缩旧日志
- 全局捕获：`Application.logMessageReceived`（Unity 日志）+ `AppDomain.CurrentDomain.UnhandledException`（托管异常）+ `Application.logMessageReceivedThreaded`（真机线程），统一写入崩溃转储文件
- 编辑器内日志面板：过滤、按级别染色、一键导出，服务灰盒期测试

### 埋点协议

统一事件模型：

```
EventData {
  name:      string        # 事件名（命名空间:动作，如 battle:enter）
  ts:        long          # 时间戳(ms)
  sessionId: string        # 本次运行会话 id
  version:   {code, res}   # 运行时版本
  ctx:       map           # 上下文（关卡 id、角色 id、玩家等级等）
  params:    map           # 事件参数（数值型）
}
```

- 写入路径：事件 → 内存队列 → 批量落盘（本地 JSON 文件，按会话分片）→ 可导出/上传（本地模拟"上报"按钮，未来接真实后端）
- 队列上限与降级：队列满时丢弃低优先级事件（保留 Error/Fatal），不影响游戏主线程

### 关键埋点清单

| 事件 | 触发点 | 关键参数 | 用途 |
|------|--------|----------|------|
| `battle:enter` | 进战斗 | 关卡 id、编队、战力 | 关卡难度评估 |
| `battle:settle` | 结算 | 评价、用时、承伤、存活 | 手感与平衡复盘 |
| `battle:switch` | 切人 | 时机、前后角色 | 切人机制有效性 |
| `battle:lock` | 锁定命中 | 命中率、修正命中占比 | 锁定手感调参 |
| `battle:death` | 角色阵亡 | 敌人类型、位置 | 难度曲线 |
| `gacha:draw` | 抽卡 | 卡池、次数、结果 | 概率校验 |
| `grow:upgrade` | 养成升级 | 对象、材料、前后战力 | 成长曲线 |
| `currency:change` | 货币变动 | 货币、数量、原因 | 经济平衡 |
| `load:scene` / `load:resource` | 加载完成 | 耗时、资源名 | 加载性能 |
| `error` / `fatal` | 异常 | 堆栈摘要、上下文 | 问题收集 |

### 与灰盒测试的配合

- 灰盒阶段每场试玩自动产出完整日志 + 埋点文件，复盘时按 `sessionId` 对齐日志与埋点
- 数值调整后对比 `battle:settle` 分布，验证改动是否达到预期，而不是凭手感判断
- 这是 D14 的核心价值：单人开发缺少玩家反馈渠道，数据是唯一客观的平衡依据
