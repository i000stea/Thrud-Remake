# 技术架构设计

> 本文档定义重制工程的总体架构：QFramework 的使用方式、程序集划分、模块边界、目录规范与网络抽象层。它是后续所有实现工作的骨架。

## 架构分层

工程按四层组织，自下而上：

```
┌─────────────────────────────────────────────┐
│ 游戏模块层  Login / MainCity / Gacha /      │
│            Battle / Grow / Bag / Task       │   ← 全部在热更程序集
├─────────────────────────────────────────────┤
│ 框架层     QFramework(Arch/UIKit/AudioKit)  │
│            通用工具(对象池/事件/日志/埋点)    │   ← AOT 主程序集
├─────────────────────────────────────────────┤
│ 基础设施层 HybridCLR / YooAsset / Unity引擎  │   ← 插件与引擎
├─────────────────────────────────────────────┤
│ 数据层     配置表 / 存档 / 埋点队列 / 版本    │   ← 横跨各层
└─────────────────────────────────────────────┘
```

- 上层依赖下层，下层不感知上层。模块间不得互相 `using`，通信走 QFramework 事件与数据层。
- 数据层被各层共享：配置表驱动内容，存档驱动进度，版本信息驱动热更流程。

### QFramework 各组件在本工程中的角色

| QFramework 组件 | 用途 | 说明 |
|-----------------|------|------|
| Architecture / Model / System / Command / Event | 模块内逻辑骨架 | 现有 `BattleArchitecture` 模式推广到全部模块 |
| UIKit | UI 面板生命周期管理 | 接入后 UI 代码自动生成绑定，支持面板栈与资源热更 |
| AudioKit | 音效/音乐播放 | 封装对象池与音量控制 |
| ActionKit | 异步时序（可选用） | 过场、演出、连招序列 |
| ResKit 的 AB 方案 | 弃用 | 资源热更统一走 YooAsset；ResKit 中加密/MD5 等工具按需迁移 |

每个游戏模块（如战斗、抽卡）拥有自己的 `Architecture` 子类（`BattleArchitecture` 已存在），内部注册本模块的 Model 与 System。跨模块共享状态放在全局 `GameModel`，通过全局事件广播变化。

## 程序集划分

程序集划分直接服务于热更新目标（细节见 `02_热更新方案.md`）：

| 程序集 | 内容 | 归属 | 说明 |
|--------|------|------|------|
| `QFramework` | QFramework 框架本体 | AOT | 稳定，不进热更 |
| `Tea.Framework` | 框架层：对象池、事件、日志、埋点、网络抽象、通用组件 | AOT | 稳定，不进热更 |
| `Tea.Game` | 全部玩法模块：战斗、主城、抽卡、养成、UI | **热更** | 迭代最频繁，全量进热更 DLL |
| `Tea.Data` | 配置加载、存档读写、数据结构 | 热更 | 随内容频繁变更 |
| `Tea.EditorTools` | 编辑器工具（配置表编辑器、打包工具） | 编辑器专用 | 不进运行时包 |

热更程序集的代码全部放在 `Assets/Game/` 下并通过 `.asmdef` 隔离；AOT 框架代码放在 `Assets/Engine/` 下。HybridCLR 的补充元数据（AOT 泛型）在构建时自动生成。

## 目录规范

重建后的 Assets 目录结构（目标状态）：

```
Assets/

    Logging/             # 分级日志
    Telemetry/           # 数据埋点
    Network/             # 网络抽象层接口
    Utility/             # 通用工具
  Game/                  # 热更程序集（Tea.Game + Tea.Data）
    App/                 # 应用入口、启动流程、场景编排
    Modules/
      Login/
      MainCity/
      Gacha/
      Battle/
      Grow/              # 养成
      Bag/               # 背包
    Shared/              # 跨模块共享代码（严格限制使用）
    UI/                  # 各模块 UI 面板（UIKit 生成）
    Data/                # 配置表加载、存档、数据结构（Tea.Data）
  Art/                   # 美术资源（YooAsset 分组管理）
    Characters/          # 角色模型/动画
    Weapons/
    Environments/        # 关卡/主城/天空盒
    UI/                  # 图集与界面资源
    Effects/
    Audio/
  Scenes/
  Plugins/               # HybridCLR、YooAsset 等第三方插件
  QFramework/            # 现有，保持不变
  01_Scenes/ 02_Scripts/ # 旧目录 → 迁移后清理
  03_Module/ 04_Prefabs/ 05_Textures/  # 旧资源目录 → 归入 Art/ 后清理
```

命名规范：

- 命名空间与目录一一对应：`TeaGame.Battle` → `Assets/Game/Modules/Battle/`
- 新旧命名空间统一为 `TeaGame.*`，旧 `TeaFramework.*` 仅保留在框架层迁移期间过渡，迁移完成后废弃
- 类型命名：System 以行为动词命名（`BattleRoleSystem`）、Model 以状态名词命名（`BattleStateModel`）、事件以过去式/完成态命名（`BattleRoleSwitchedEvent`）

## 场景与流程编排

当前场景链为 `0Login → 1Main → 2Gacha → 3Battle`，另有游离的 `4BattleScene-Test0/1`。重建后：

- 保留单场景入口 `0BootScene`（或沿用 Login 场景），负责：初始化框架 → 热更检查/下载 → 加载配置 → 进入主流程
- `3BattleScene` 与测试场景统一为 `BattleScene`，作为战斗模块的容器场景，由模块按需加载
- 主城为 2D 功能页，不再需要独立 3D 场景（主城场景资产保留，供后续升级 3D 主城时使用）
- 场景切换统一走 `SceneManager` 流程控制器（`AppSceneController`），支持加载进度、预加载下一场景资源

启动流程（伪代码）：

```
Boot()
 ├─ QFramework 初始化
 ├─ YooAsset 初始化 + 版本检查（见热更方案）
 ├─ HybridCLR 加载热更 DLL（若有更新）
 ├─ 加载全局配置表（角色/武器/关卡/掉落）
 ├─ 读取本地存档
 ├─ Login 流程（本地占位）
 └─ 进入 MainCity 2D 功能页
```

## 模块边界与通信

模块独立性是本工程"合理"标准的核心要求。约束如下：

- 每个模块自带入口 `IXxxModule`，只暴露 Init / Shutdown / 对外命令，不暴露内部类
- 模块内状态在模块内 Model 中；跨模块数据一律经全局 `GameModel` 或存档读写
- 模块间通信使用 QFramework 全局事件（如 `BattleEnteredEvent`、`GachaResultEvent`、`BagItemChangedEvent`），消费者在事件表集中登记
- 任何模块不得 `new` 另一个模块的 System/Model，统一通过各自 Architecture 获取
- 共享工具（对象池、日志、埋点）归框架层，模块只调用不实现

事件表示例（后续在实现中维护成独立文件）：

| 事件 | 方向 | 触发方 → 消费方 |
|------|------|-----------------|
| `BattleEnteredEvent` | 主城 → 战斗 | 携带关卡 ID 与编队数据 |
| `BattleSettledEvent` | 战斗 → 主城/养成 | 携带评价、掉落、用时 |
| `BagItemChangedEvent` | 养成/抽卡 → 背包 UI | 携带变更的物品与数量 |
| `HeroUnlockedEvent` | 抽卡 → 编队/图鉴 | 携带角色 ID |

## 网络抽象层（P2P 预留）

本期为纯本地单机，但接口层现在就搭好，避免日后联机改造伤筋动骨：

```csharp
public interface INetworkService
{
    void Connect(ConnectOptions options, Action<bool> onResult);
    void Disconnect();
    bool IsConnected { get; }
}

public interface IRealtimeService   // 供 P2P 联机使用
{
    void CreateRoom(RoomConfig config, Action<RoomResult> onResult);
    void JoinRoom(string roomId, Action<RoomResult> onResult);
    void SendReliable(int channel, byte[] payload);
    void OnReceive(Action<int, byte[]> handler);
}

public interface IBattleSnapshot   // 战斗状态序列化点，供联机同步
{
    byte[] SerializeFrame(int frameIndex);
    void   RestoreFrame(byte[] snapshot);
}
```

- 当前提供 `LocalNetworkService`（本地占位实现），后续可替换为 Steam P2P、自研 UDP 或第三方联机 SDK，替换点仅在框架层
- 战斗的联机同步策略（预测/回滚、帧同步 vs 状态同步）不在本期范围内，但 `IBattleSnapshot` 要求战斗逻辑在关键状态处具备可序列化能力，实现时注意避免把 Unity 对象直接塞进快照

## 编码与工程纪律

- 代码注释与提交信息使用中文
- 模块内不允许出现 `Instantiate/Destroy` 的高频调用路径（见性能文档，统一走对象池）
- 不允许模块间 `using`；跨模块引用触发 Code Review（单人开发时以搜索检查代替）
- 配置数据不允许硬编码在类中（伤害、CD、掉落等一律进配置表）
- 热更程序集内禁止使用 `UnityEditor` API；编辑器工具单独放 `Tea.EditorTools`
