# 热更新方案（HybridCLR + YooAsset）

> 本文档定义代码热更与资源热更的完整方案：程序集策略、资源分组、更新流程、版本管理、本地模拟与打包调试工作流。技术选型已确认（决策 D02）。

## 目标与边界

- 代码热更：玩法逻辑（`Tea.Game`）全部进热更 DLL，发版后修复 Bug、调数值、加内容均不需重新上架
- 资源热更：美术、配置、音频等全部走 YooAsset 管理的 AssetBundle，支持按需下载与增量更新
- 本地模拟：单人开发阶段用本地文件服务器模拟"客户端 → 更新服务端"的完整流程，不依赖线上环境
- 本期不做：加密上线级 CDN、灰度、AB 包加密混淆（保留接口与开关，后续按需开启）

## 程序集与热更边界

```
AOT 主包（随安装包发布）
 ├─ Unity 引擎 + QFramework + Tea.Framework（框架层）
 ├─ HybridCLR 运行时 + YooAsset
 └─ 首包资源（核心关卡/角色/UI）

热更内容（运行时下载）
 ├─ Tea.Game.dll + Tea.Data.dll（全部玩法代码）
 ├─ 热更资源（新关卡/新角色/新配置）
 └─ 补充元数据 AOT 泛型 dll（HybridCLR 生成）
```

划分理由：玩法迭代最频繁，代码全进热更可最大化热更价值；框架层稳定，进 AOT 可减少补元数据风险。若日后某个模块需要 AOT 化（如性能敏感的高频数值计算），按模块拆分热更程序集即可平滑调整。

### AOT 泛型补充元数据

HybridCLR 的核心限制是 AOT 程序集的泛型实例化。规避策略：

- 热更代码中谨慎使用 `List<T>` / `Dictionary<TK,TV>` 等泛型的非常见实例化（如嵌套泛型）
- 构建时开启 HybridCLR 的补充元数据生成（`AOTGenericReferences`），把引擎与框架层可能涉及的全部 AOT 泛型打补丁
- 建立一条纪律：新增框架层泛型 API 时，在编辑器工具中登记进补充元数据列表

## YooAsset 资源分组

按加载时机与更新频率划分：

| 分组 | 内容 | 更新频率 | 说明 |
|------|------|----------|------|
| `shared` | 公共图集、字体、通用 UI | 低 | 首包内置，全模块共享 |
| `battle` | 敌人模型、子弹特效、战斗 UI、灰盒关卡 | 中 | 战斗模块，随关卡迭代更新 |
| `role` | 角色模型/动画 | 低 | 新角色发布时更新 |
| `weapon` | 武器模型/特效 | 低 | 同上 |
| `gacha` | 抽卡场景/动画/卡面 | 中 | 第二里程碑启用 |
| `maincity` | 主城资产（含预留的 3D 主城） | 低 | 2D 功能页阶段仅存未用 |
| `audio` | 音乐/音效 | 低 | 按需下载 |
| `config` | 配置表（JSON） | 高 | 数值调整即时生效 |

- 首包策略：`shared` + `battle` 核心关卡 + 最小 `role/weapon`（灰盒阶段体积很小，全打首包也可）
- 大资源（BGM、高模）走"运行时按需下载"模式，进度 UI 复用启动下载流程

## 更新流程

```
客户端启动
 ├─ 读本地版本（VersionManifest）
 ├─ 请求远端版本清单（本地模拟服务器 / 真实 CDN）
 ├─ 比对：资源清单差异 → 下载增量 AB（断点续传）
 ├─ 比对：代码版本 → 下载新 Tea.Game.dll 与补元数据
 ├─ 更新本地清单并持久化
 ├─ HybridCLR 加载热更程序集
 └─ 进入启动流程（见架构文档）
```

版本字段设计：

| 字段 | 含义 | 变更时机 |
|------|------|----------|
| `AppVersion` | 客户端安装包版本（`1.0.0`） | 原生代码或框架层改动 |
| `CodeVersion` | 热更 DLL 版本（自增） | 热更代码改动 |
| `ResVersion` | 资源清单版本（自增） | 任意资源改动 |
| `Channel` | 渠道标识（`local` / `pc` / `android`） | 打包时写入 |

判断规则：`AppVersion` 不同 → 提示重新下载安装包；相同则只比较 `CodeVersion` 与 `ResVersion`，各自增量更新。

## 本地模拟服务器

单人开发必须能离线走通完整热更流程。方案：

1. 用 YooAsset 提供的 Hosting Server（或任意静态文件服务器，如 `npx serve` / `python -m http.server`）托管 `BuildTarget/` 输出的更新目录
2. 编辑器工具一键生成"增量版本"：改一个配置/一张图/一段代码 → 执行构建 → 生成新版本清单 → 覆盖到服务器目录
3. 真机/PC 包设置服务器地址为 `http://127.0.0.1:8080/`（PC）或局域网地址（Android 真机）
4. 验证路径：启动 → 版本比对 → 下载增量 → 加载新 DLL → 运行新内容

调试开关（`DevSettings`，仅 Debug 构建）：

- `ForceSkipUpdate`：跳过热更直接跑本地内容，用于纯编辑器开发
- `ClearLocalCache`：清空本地下载缓存，模拟全新安装
- `LogUpdateDetail`：打印版本比对与下载明细

## 构建与打包工作流

分平台构建矩阵（`Tea.EditorTools` 提供一键脚本）：

| 目标 | 用途 | 构建内容 |
|------|------|----------|
| Editor | 日常开发 | 不构建 AB，直接加载 `Assets/Game` 源码与 `Art` 原始资源 |
| PC Standalone | 本地验证 | AOT 主包 + 热更 DLL + AB |
| Android APK | 移动端验证 | AOT 主包 + 首包 AB，热更走本地服务器 |

关键流程：`HybridCLR/Generate/All` → 编译热更程序集 → `HybridCLR/CompileDll` → YooAsset 构建 AB → 生成版本清单 → 打包主程序。

一条纪律：**编辑器运行模式永远从源码加载，AB 模式只在真机/PC 打包后验证**。二者内容不一致时优先怀疑构建配置，避免"编辑器能跑、打包不行"的排查地狱。

## 风险与规避

| 风险 | 说明 | 规避 |
|------|------|------|
| AOT 泛型缺失崩溃 | 热更代码触发未补的泛型实例化 | 补充元数据 + 泛型使用纪律（见上） |
| 首包体积膨胀 | AB 全塞首包 | 分组策略 + 压缩（LZ4） + 按需下载 |
| Windows 与 Android 清单不一致 | 平台相关 AB 名/依赖差异 | 构建矩阵按平台隔离输出目录，清单按平台生成 |
| 热更后旧存档不兼容 | 数据结构变更 | 存档版本号 + 迁移脚本（见外围系统文档） |
| 本地服务器目录被多平台覆盖 | 版本清单混乱 | 服务器目录按 `Channel/平台` 分子目录 |

## 与现有 QFramework ResKit 的关系

`Assets/QFramework/Toolkits/ResKit` 自带 AB 加载与 HotFixScripts（MD5/AES/RSA/下载器），但其下载链路与现代资源管线相比缺少断点续传、清单校验、按需加载等能力。决策：

- 资源层统一使用 YooAsset，不再使用 ResKit 的 AB 实现
- ResKit 中可复用的加密（AES/RSA）、MD5 工具按需迁移到 `Tea.Framework`（后续开启 AB 加密时启用）
- UIKit 照常接入（UI 面板生命周期与资源加载点由 UIKit 调用 YooAsset，适配层在框架层完成）
